1. THE NAMING OF THIS STANDARD
================================================================================

The 3 names of this design, and the form of each:

    project        <tier>-<project>              t2-transcriptextraction-summary
    group          <tier>-<project>.<group>      t2-transcriptextraction-summary.window
    file           nNNNN.<tier>-<project>.[<name>].go
                   n0410.t2-transcriptextraction-summary.[window].go

The 3 names share 1 prefix, so a reader who sorts the folders sees the
project, then its groups, then the files of each group.

## The 1 difference from the nanoGPT design

Go forbids a dot in a package folder name, and a Go package is 1 folder. The
nanoGPT design names a group `<tier>-<project>.<group>` and puts its files in
that folder. This app cannot, so the group becomes a sub-folder of the project
folder:

    folder   internal/t2-transcriptextraction-summary/window/
    package  window
    file     n0410.t2-transcriptextraction-summary.[window].go

The group name is still `<tier>-<project>.<group>` in this file and in the
project list, and the folder path states it as 2 path segments. A reader who
sorts `internal/` sees the projects in tier order, and a reader who sorts a
project folder sees the groups in group order, then the files in import order.

2. THE TIER ASSIGNMENT
================================================================================

The tiers run t0 < t1 < t2 < t3 < t4 < te. A project sits in the lowest tier
that holds every project it imports, plus 1.

    tier   project                          what it holds
    -----  -------------------------------  --------------------------------
    t0     t0-transcriptextraction-table    the CSV table and the text rules:
                                           the folder paths, the URL and arXiv
                                           and DOI patterns, the word count,
                                           the message key, the month, and the
                                           rune-safe cut
    t1     t1-transcriptextraction-export   the Telegram export read and the
                                           6 side tables
    t1     t1-transcriptextraction-split    the 3 split modes and the part
                                           tables
    t1     t1-transcriptextraction-reference the 14 reference kinds and the
                                           rule extraction over every message
    t1     t1-transcriptextraction-translate the English text of a Cyrillic
                                           message
    t2     t2-transcriptextraction-summary  the summary windows and their
                                           prompt
    t2     t2-transcriptextraction-relevance the relevance windows, the solo
                                           vote, and the consensus
    t2     t2-transcriptextraction-photo    the photo table, the photo prompt,
                                           and the photo index
    t2     t2-transcriptextraction-aggregate the summary parse, the rollup
                                           prompt, and the index tables
    t3     t3-transcriptextraction-job      the durable job: the unit, the
                                           store, the pi call, the answer
                                           check, and the progress line
    t4     t4-transcriptextraction-chain    the unit list of each job and the
                                           stage chain
    te     te-transcriptextraction-main     the 12 subcommands and the 2
                                           commands

The 4 t1 projects import only `t0-transcriptextraction-table`, so they share a
tier and import nothing of their own tier. The 4 t2 projects import t1 and t0,
so they sit in t2. `t3-transcriptextraction-job` imports t0 only, but it sits
in t3 because the t4 chain imports it and the t2 stages do not. The 2 te
commands import every tier.

## Why the job sits above the stages

`t3-transcriptextraction-job` imports `t0` alone, so the tier rule alone would
put it in t1. It sits in t3 for 2 reasons:

- The chain of t4 calls the job, and the job calls no stage. A job that sat in
  t1 would let a t1 stage import the job, and then the job would call the stage
  that imports it.
- The job is the only project that runs a model call, so a reader who reads the
  tier list sees the model boundary at t3 and above.

The import check of section 9 still passes, because t3 imports only t0.

6. THE FILE NAME OF EACH TYPE
================================================================================

The operator states 3 rules for a file name:

- 1 type, 1 function, or 1 constant block per file.
- The file name starts with a lowercase `n` and a 4-digit number, and the
  number states the position of the file in the import order of its project.
- The file name states the tier and the project, so a reader who reads the
  file name knows the tier and the project without reading the folder path.

The form of the file name is:

    nNNNN.<tier>-<project>.[<name>].go

    nNNNN       the position of the file in the import order of its project.
                The number is 4 digits, and it steps by 100 for each project
                and by 10 for each group, so a later split has room for a new
                file without a renumber of the files beside it.
    <tier>      the tier of the project that holds the file: t0, t1, t2, t3,
                t4, or te.
    <project>   the project name of the file, for example
                transcriptextraction-summary.
    <name>      the group name in kebab-case, for example `window`.

a reader who sorts the file names sees the projects in tier order.

The 2 commands `transcriptextraction` and `csvcheck` are 2 entry points, so
they take 2 blocks of the 1 te project. The block `n1300` is the second entry
point, and the gap `n1220` to `n1299` stays free for a later subcommand.

## The Go name inside the file

Go requires a package name, and the package name is the group name in
lowerCamelCase, because a Go package name holds no hyphen:

    folder   internal/t2-transcriptextraction-summary/window/
    package  window
    type     Window
    file     n0600.t2-transcriptextraction-summary.[window].go

The type name is PascalCase, as Go requires. The `<name>` part of the file
name is the kebab-case form of the group name, so `Window` sits in
`n0600.t2-transcriptextraction-summary.[window].go`.

8. THE IMPORT ORDER OF 1 GROUP, WORKED
================================================================================

This section shows the numbering rule of section 6 on 1 project, so a reader
can check the rule against a real folder.

The project `t3-transcriptextraction-job` owns the block `n1000` to `n1099`.
Its 5 groups take 5 blocks of 10 numbers:

    .store     n1000   n1000.t3-transcriptextraction-job.[store].go
    .call      n1020   n1020.t3-transcriptextraction-job.[call].go
    .answer    n1030   n1030.t3-transcriptextraction-job.[answer].go
    .run       n1040   n1040.t3-transcriptextraction-job.[run].go
    .lock      n1060   n1060.t3-transcriptextraction-job.[lock].go

The numbers `n1001` to `n1009`, `n1011` to `n1019`, and the rest of each block
stay free, so a later file takes the next free number of its block and no file
beside it moves.

A reader who sorts the project folder sees the group order first, because the
number is the first 5 characters of the file name.

================================================================================
10. WHAT THIS DESIGN DOES NOT DECIDE
================================================================================

- The name of each type. This design gives each file a group name, and the
  type inside the file takes the PascalCase form of that name. The operator
  confirms a type name before the rename.
- The translation stage. This design gives it a project, 2 groups, and 2 file
  names, and the code of it is written in a later step.
- The 2 commands `transcriptextraction` and `csvcheck`. This design gives each
  one a block, and the build script keeps 2 binaries.

================================================================================
11. THE STEPS THAT APPLY THIS DESIGN
================================================================================

1. Write `00-projects-and-groups.txt` at the repository root with the content
   of section 3.
2. Create each project of section 2 as a folder, and each group as a
   sub-folder.
3. Move each declaration of section 7 into its group folder, with the file
   name of section 6.
4. Replace the 7 `cutText` copies and the 4 `boolText` copies with
   `textrule.CutRuneText` and `textrule.BoolText`.
5. Run `go build ./...` and confirm there are no errors.
6. Run the import check of section 9 and confirm every project passes.
