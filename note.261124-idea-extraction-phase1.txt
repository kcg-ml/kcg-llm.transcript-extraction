# Phase 1 of the idea extraction: what it is and what it measured

Date: 2026-11-24

## What it is

Phase 1 extracts 5 of the 14 summary fields into their own table, with the
message id beside every item: PAPERS, TALKS, CODE, METHODS, MODELS.

The 5 fields name a thing a reader can look up. The other 9 fields need the
whole argument of a window, so a later phase takes them.

| piece | path |
| --- | --- |
| prompt and window table | `internal/t2-transcriptextraction-idea/ideaprompt/` |
| answer parser and item table | `internal/t2-transcriptextraction-idea/ideaparse/` |
| job name | `chainunit.JobNameIdeaExtraction` = `idea-extraction` |
| timeout | `chainunit.TimeoutSecondsIdeaExtraction` = 483s |
| subcommands | `idea-windows`, `idea-index` |
| window table | `data/idea_windows.csv`, 1042 rows |
| item table | `data/idea_items.csv` |
| prompts | `prompts/idea-extraction-<window_id>.txt` |
| answers | `model-answer/job/idea-extraction/done/<window_id>.txt` |

## The prompt file name carries the prefix

The idea prompt is `prompts/idea-extraction-<window_id>.txt`, not
`prompts/<window_id>.txt`. Both this stage and the summary stage name their
prompt after the same 10-message window id, so a shared file name lets one
stage overwrite the other's prompt. The first version of this stage did exactly that and destroyed 1042
summary prompts; `transcriptextraction windows` restored them, and `git status
prompts/` then showed no change.

## What the prompt reads

The prompt holds the 10-message summary of the window first, then the
messages themselves. The summary is the text this stage extracts from: it
already names the papers, talks, repositories, methods, and models of the
window, in one place. The messages follow so the model can find the message id
of each entry, because the summary table holds no message id.

The first version of this stage read the raw messages only and never read a
summary. An auditor rejected that as a different stage from the one the
objective names, and the prompt was rewritten to read the summary.

A bare Telegram id is resolved against `data/messages.csv`, because the model
sometimes writes `593111` where the prompt asks for `593111-251120`. Without
that resolution 5 of the 17 rows of the second sample carried no message key.

## Measured on 5 windows

| measure | value |
| --- | --- |
| probe, 1 call, summary-reading prompt | 7.4s, 1079 chars, 145.2 chars/s |
| 5-window sample | 5 of 5 ok, 0 failed, 8.3s for the last answer |
| items from 5 windows | 17 rows, every row carries a message key |

The 17 rows split as METHODS 9, TALKS 4, PAPERS 2, MODELS 1, CODE 1. Every
message key was checked against `data/messages.csv` and all 17 resolve to a
real message.

## The timeout is an estimate, not a measurement

`TimeoutSecondsIdeaExtraction` is 483s, taken from the
summary-window-of-10-messages p95 of 121s. This job has no measured calls yet,
so the bound is borrowed from the job that reads the same 10 messages and
writes a longer answer. A measured p95 replaces it after the first full run.

## The 6 prompts that still hold Cyrillic

6 of the 1042 idea prompts hold Cyrillic letters after the translation stage.
Each one is a case the translation stage accepts: a 2-letter fragment (`Уе`,
`Гр`), a Russian name inside an English sentence (`Subbotniks (Russian:
Субботники, IPA:`), an English sentence that quotes a Russian example, and a
Telegram hashtag (`#обзор@UAVDEV`). No prompt holds an untranslated Russian
sentence.
