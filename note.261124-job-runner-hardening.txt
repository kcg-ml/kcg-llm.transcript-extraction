# The job runner hardening: what each requirement changed and how it was checked

Date: 2026-11-24

## Req 8: the layers, and what the merge did and did not save

The merge is measured on its own, against the code it touched:

| change | files | lines |
| --- | --- | --- |
| `unit` merged into `store` | -1 | -127 |
| `progress` merged into `run` | -1 | 0 (2-line rename of `unit/n1000` to `store/n1000`) |
| groups | 7 -> 5 | |

So the merge removed 3 files and 127 lines. The group count dropped from 6 to
5, and the import layers with it.

The file count of the package as a whole rose, and the objective's "not more
files" is only half met. The rise is not the merge: it is the 6 behaviours
Req 4, 5, 6, and 7 added, which had no file before:

| new file | holds |
| --- | --- |
| `call/n1022` | `StallRecord`, the trickle rule, the floor constants |
| `store/n1013` | the live status file that `--status` reads |
| `run/n1041` | the progress line and its 60s window |
| 4 `n9900.*._test.go` | 12 tests over 4 packages |

The package now holds 14 files and 1989 lines of non-test code, plus 4 test
files. A behaviour the objective requires cannot be added without a place to
put it, so the count is the cost of Req 4, 5, 6, and 7 and not of the merge.

## Req 4: the 2 kill rules

A call is killed for a stall in 2 ways, and the failure file says which:

| rule | fires when | reason text |
| --- | --- | --- |
| no growth | stdout has not grown for the stall bound, counted from the start of the call | `stall: no output for 3s, process killed` |
| trickle | the call has written for 30s and writes under 10 chars/s | `stall: trickled 0.56 chars/s for 30s, under the 10 chars/s floor, process killed` |

Both rules are distinct from the timeout: a stall exits 125 and writes
`"stall": true`, and a timeout exits 124 and writes `"stall": false`.

### The stall bound is per job: 90s, or above the slowest measured call

The provider this pipeline uses does not stream: it holds the whole answer
and writes it at the end. Measured directly against `pi`:

| prompt | total | first byte | chars |
| --- | --- | --- | --- |
| 7191 chars | 7.7s | 5.7s | 962 |
| 181224 chars | 315.0s | 313.0s | 141495 |

So a call that has written nothing may be thinking, and a flat 90s bound
kills it. The first version of the trickle rule measured the rate from the
start of the call and killed 24 whole-chat units at 30s with 0 chars, and it
would have killed 30% of the 5194 healthy calls (1537 took over 30s) and 6%
(318 took over 90s).

`chainunit.StallSecondsOf` returns the larger of 90s and 15% above the
slowest measured call of the job, and every bound is under that job's
timeout, so the stall rule fires before the timeout and the failure says
which:

| job | slowest call | stall bound | timeout |
| --- | --- | --- | --- |
| message-translation | 46.9s | 90s | 145s |
| photo-content | 84.0s | 97s | 173s |
| relevance-window-vote | 200.7s | 205s | 212s |
| summary-window-of-10-messages | 209.3s | 241s | 483s |
| summary-window-of-100-messages | 380.1s | 438s | 1206s |
| summary-window-of-one-month | 475.3s | 547s | 1901s |
| summary-window-of-whole-chat | 547.6s | 630s | 2015s |
| idea-extraction | 8.3s | 90s | 483s |

The `--stall` default is 90s, which is the floor of the table, so a job whose
bound is 90s takes the flag value and a job above it takes its own. `--stall
0` also takes the job's bound.

`relevance-window-vote` is the tight case: its slowest healthy call is 200.7s
and its timeout is 212s, so a bound 15% above the slowest call would be 231s
and the timeout would kill first. 205s keeps both rules live.

2 tests in `chainunit/n9900.chainunit.chainunit._test.go` hold the table
honest: `TestStallBoundIsUnderTheTimeout` fails if any bound reaches its
timeout, and `TestStallBoundIsAboveTheSlowestMeasuredCall` fails if any bound
is at or under a measured healthy call. The second test caught a real defect
while it was being written: the first table gave relevance 190s, under its
200.7s call.

### The verification

The requirement's own check is a fake `pi` that sleeps without output. It is
killed at the stall bound and the failure file says stall:

```
$ PI_BIN=/tmp/fakepi/pi transcriptextraction job --job relevance-window-vote \
    --jobs 1 --stall 3 --timeout 600 --retries 0
{"attempt":1,"chars":0,"code":125,"error":"stall: no output for 3s, process killed",
 "seconds":3,"stall":true,"unit_id":"relevance-window-vote-00807-v2"}
```

`evidence.261124-job-runner/stall-failure-sample.json` holds that file, and
`evidence.261124-job-runner/errors-log-sample.txt` holds the matching
`logs/relevance-window-vote.errors.log` lines. Both were regenerated from a
live run of the current code.

4 Go tests in `call/n9900.call.call._test.go` cover the rules:

| test | what it proves | measured |
| --- | --- | --- |
| `TestSilentCallIsKilledAsStall` | a call that never writes dies at the stall bound | killed at 3.0s, exit 125 |
| `TestNoGrowthIsKilledAsStall` | a call that stops after its first byte dies at the bound | killed at 3.5s |
| `TestTrickleIsKilledAsStall` | a slow drip after the first byte is killed | killed at 33.5s |
| `TestLateWholeAnswerSurvives` | a call that thinks 60s then writes is not killed | survived, 60.4s, 63 chars |

The last test is the guard against the bug: a healthy call that is slow to
start must not be killed. Verified against the real provider too: `job --job
summary-window-of-whole-chat --probe` ran 308.6s and returned 141449 chars
with the default bound.

## The exit codes

A job ends with a code that says why it stopped: 0 ok, 1 a settings or store
error, 2 units failed, 3 another process holds the lock. The command layer
turned every error into exit 1, so a script could not tell a lock refusal from
a failure. `subcommand.ExitCodeError` now carries the code through, and
`subcommand.ExitCodeOf` reads it. Verified: a second run on a held lock exits
3, and a bad flag still exits 1.

## Req 6: the calls in flight

The in-flight count lives in the memory of the running process, and `--status`
is a second process that reads files only. The runner therefore writes
`model-answer/job/<job>/live.status` every 2 seconds, and `--status` reads it.
A finished run removes the file, so a stale count is never shown.

Measured: a run with `--jobs 2` answers `inflight=2`, and a finished run
answers `inflight=0`.

## Req 1: the lock file is never empty

The first version created the lock file and then wrote the pid into it. A
second process that read the file in that window saw no pid and reclaimed a
live lock. The record is now written to a temporary file and linked into
place, so the lock file never exists empty. `os.Link` fails with `EEXIST` when
the lock exists, so 1 process still takes the lock.

`TestLockFileIsNeverEmpty` runs 200 acquire/release rounds while a reader
polls the file, and the file is never seen empty.
